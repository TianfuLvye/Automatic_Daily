## Lab 0 · 地基

### Q1. 标题被微调一个字,`content_hash` 就变了,得到两条记录。这是 bug 还是 feature? ⚖️

**答:在我给的实现里这题不成立,而这正是答案的一部分。**

先看现象的严重性:平台修改热搜标题是**高频事件**(微博几乎每小时都在微调措辞)。如果 hash 对标题敏感,同一条热搜一天能在你库里变出 5 条记录,报纸上就会出现 5 条几乎一样的内容。这是必须解决的问题。

标准解法是**分层**:

| 层级 | 用什么 | 抗什么 |
|---|---|---|
| L1 精确 | `source + normalized_url` | 追踪参数、移动端域名、末尾斜杠 |
| L1' 退化 | `source + normalized_title` | 仅当 URL 缺失时(部分热榜不给链接) |
| L2 近似 | SimHash 汉明距离 ≤ 3 | 标点、语气词、少量改写 |
| L3 语义 | embedding 余弦 ≥ 0.82 | 完全重写的同一事件 |

我的参考实现里 `compute_hash()` **优先用 URL 而不是标题**,所以标题微调根本不影响 hash——这才是根治。标题只在没有 URL 时作为退化方案使用,并且先过 `normalize_title()` 剥掉标点和序号。

**那什么时候「标题变化产生新记录」是 feature?**

一种情况:你想追踪**平台对同一事件的措辞变化**。比如某条热搜从「XX 公司回应质疑」被改成「XX 公司致歉」,这个措辞转向本身就是有价值的情报信号。但这属于**独立的观测需求**,应该建一张 `title_history(content_hash, title, observed_at)` 表专门记录,而**不是**通过污染主键来实现。

> **可提炼的原则:主键是身份,不是状态。任何会变的东西都不该进主键。**

### Q2. 为什么 `rank` 和 `heat` 不能参与 hash?想记录排名变化曲线,表结构该怎么改?

**为什么不能参与**:热搜的 `rank` 每次采集几乎必然变化。若参与 hash,每 30 分钟采一次,一条热搜一天就产生 48 条记录,去重完全失效,数据库还会膨胀。

这背后是一个通用的建模区分:

- **实体(entity)**:一条内容本身 → `items` 表,主键稳定,一条内容一行
- **观测(observation)**:某时刻这条内容的状态 → `rank_snapshots` 表,时序数据,一条内容多行

**表结构**(参考实现 `core/store.py` 已包含):

```sql
CREATE TABLE rank_snapshots (
    content_hash TEXT NOT NULL,
    board        TEXT NOT NULL,     -- 同一条内容可同时在多个榜上
    rank         INTEGER NOT NULL,
    heat         REAL,
    observed_at  TEXT NOT NULL,
    PRIMARY KEY (content_hash, board, observed_at)
);
CREATE INDEX idx_snap_board ON rank_snapshots(board, observed_at);
```

三个设计细节值得注意:

1. **`board` 必须进主键**。一条内容可能同时在「微博热搜」和「微博要闻」榜上,名次不同。
2. **主键含 `observed_at`** 天然实现了「同一时刻重复采集不会重复写入」。
3. `items.rank` 保留最后一次值,是**冗余字段**,纯为查询方便。冗余在这里是合理的——你 99% 的查询只关心当前名次。

有了这张表,「蹿升检测」才写得出来:

$$ \Delta r = r_{\text{first}} - \min_{t \in W} r_t $$

注意我用**窗口内最优名次**而不是最新名次。理由:很多爆点是「冲上去又掉下来」的,用最新名次会完全错过它们,而这类内容往往正是当天最值得记录的。

### Q3. `published_at` 拿不到时用 `fetched_at` 兜底,会带来什么后果?

**会,而且后果比想象的严重。** 至少三条:

**1. 时效性打分全面失真。** 你的打分函数里有乘性衰减因子 $0.5^{t/T}$。如果所有拿不到发布时间的条目都用 `fetched_at`,它们的年龄永远是 0,永远拿满分新鲜度。结果:**元数据质量差的源会系统性地挤掉元数据完整的源**。这是一种隐蔽的算法偏见——它奖励的是「接口做得烂」,而不是「内容好」。

**2. 冷启动时的时间坍缩。** 你第一次跑系统,RSS 一次性返回过去两个月的 50 篇文章。全部盖上今天的 `fetched_at`,你的第一份报纸会把两个月前的旧闻当作今日新闻推给你。

**3. 历史分析永久失效。** 「我关注的话题在过去三个月的讨论量趋势」——只要时间字段被污染,这类分析就再也做不了,而且**不可回溯修复**。

**正确处理(按优先级降级)**:

```python
def resolve_published_at(item, raw) -> tuple[datetime, str]:
    """返回 (时间, 置信度标记)。置信度必须落库,不能丢。"""
    if t := parse_from_api_field(raw):        return t, "exact"
    if t := parse_from_html_meta(item.url):   return t, "exact"    # og:published_time
    if t := parse_from_url_path(item.url):    return t, "day"      # /2026/08/06/
    if t := parse_from_text(item.title):      return t, "fuzzy"    # 「3小时前」
    return item.fetched_at, "unknown"
```

关键是**加一个 `time_confidence` 字段**,并在打分时区别对待:

- `exact` → 正常参与时效计算
- `day` → 当天 12:00 兜底
- `unknown` → **时效因子固定给 0.5 的中性值**,既不奖励也不惩罚

> **通用原则:兜底值必须带标记。无标记的兜底是在往数据里注入无法追溯的谎言。**

### 验收标准实现要点

- **`normalize_url` 的隐藏难点**:不能无脑剥所有参数。`mp.weixin.qq.com` 的 `__biz/mid/idx/sn` 四个参数**就是内容 ID**,剥掉整个链接就废了。所以我用了**按 host 的白名单/黑名单双模式**(见 `core/schema.py` 的 `_ESSENTIAL_PARAMS`)。这是实际会踩的坑。
- **幂等的正确写法**:用 `INSERT OR IGNORE` + `cursor.rowcount` 判断,**不要**先 `SELECT` 再 `INSERT`——两个 collector 并发时有竞态窗口。
- **WAL 模式**必开,否则并行采集必然 `database is locked`。

## Lab 1 · 热榜聚合

### Q1. 30 分钟采一次 vs 5 分钟采一次,分别漏掉什么?采样间隔的下界由什么决定?

这是一道**采样定理**题,可以定量回答。

设一条热搜在榜上的停留时间为 $T_{\text{live}}$,采样间隔为 $\Delta t$。要保证不漏,需要:

$$ \Delta t < T_{\text{live}} $$

而实际漏采概率(假设上榜时刻均匀分布)约为:

$$ P_{\text{miss}} \approx \max\left(0,\ 1 - \frac{T_{\text{live}}}{\Delta t}\right) $$

代入经验值:微博热搜尾部条目的停留时间中位数约 20–40 分钟。

| 间隔 | 对 $T_{\text{live}}=30\text{min}$ 的漏采率 | 会漏掉什么 |
|---|---|---|
| 30 min | ≈ 0%,但**边界情况必漏** | 停留 < 30min 的短命热搜 |
| 5 min | ≈ 0% | 基本不漏 |

但注意:**5 分钟采样漏掉的东西和 30 分钟不同**——5 分钟仍然会漏掉「只存在 3 分钟就被撤下」的内容,而这类内容往往恰恰是最有情报价值的(被删除的热搜)。

**下界由三个约束共同决定,取最紧的那个**:

$$ \Delta t_{\min} = \max\big(\underbrace{T_{\text{cache}}}_{\text{数据源缓存}},\ \underbrace{T_{\text{rate}}}_{\text{限流阈值}},\ \underbrace{T_{\text{cost}}}_{\text{存储/算力预算}}\big) $$

**对你的系统,决定性约束是第一项**:DailyHotApi 默认缓存约 60 分钟。这意味着——

### Q2(顺序调整,先回答缓存题). 每 5 分钟请求一次,实际数据新鲜度是多少?

**答:仍然是最坏 60 分钟,平均 30 分钟。你只是在浪费自己的 CPU 和对方的带宽,一点新鲜度都没换到。**

这是个非常值得记住的教训:**你的采样频率再高,也突破不了上游的缓存粒度。** 整条链路的新鲜度由最慢的一环决定。

那怎么办?三个选项:

1. **接受它**,把间隔调到 30 分钟(缓存周期的一半,符合奈奎斯特直觉),这对个人报纸完全够用 ——**推荐**
2. **改 DailyHotApi 的缓存 TTL**(它是你自部署的,配置能改),但这等于把压力转嫁给上游平台,要克制
3. **绕开它直连平台接口**,新鲜度最高但要自己面对反爬 —— 除非你真的需要分钟级,否则不值

> **可提炼的原则:优化前先确认瓶颈在哪一层。在非瓶颈环节上努力,是工程新手最常见的浪费。**

### Q3. 热榜是幸存者偏差数据源,对「批判性思考」目标是帮助还是伤害? ⚖️

**答:纯粹的伤害,而且伤害是双重的。必须靠架构设计对冲,而不是靠调参。**

**第一重伤害:内容层面。** 热榜的排序目标是**平台的停留时长**,不是你的认知质量。能上热榜的内容天然偏向情绪唤起度高、争议性强、认知负担低的类型。而「引起批判性思考」的内容——需要背景知识、结论反直觉、论证长——在热榜机制下系统性地被淘汰。**两个目标函数几乎正交。**

**第二重伤害(更隐蔽):共识幻觉。** 热榜只展示已经火的,你看不到「没火但更有价值的」。长期只读热榜,你会逐渐产生「大家都在关心这个」的错觉,而实际上你看到的是平台推荐系统的产物。这会**削弱**而不是增强批判性思考——因为批判性思考的前提是意识到自己看到的是一个有偏样本。

**架构上的三条对冲**:

1. **版面隔离**。热榜进「速览」版,严格限量(比如封顶 10 条),且明确标注「以下为平台热度排序,不代表重要性」。这行标注不是形式主义,它是给未来的你的提醒。
2. **深度版面用完全不同的召回源**。知乎长文、公众号、订阅博主走 RSS 通道,**打分函数里 $w_{\text{hot}}$ 直接设为 0**。让「热」和「好」在系统里走两条互不相交的路径。
3. **主动引入逆向源**。订阅几个立场/风格与主流热榜相反的信源,给它们**固定版位**而不是让它们和热榜内容竞争排名——竞争排名它们必输。

> 这道题的深层含义:**你正在构建的推荐系统,会反过来塑造你的认知**。这是做个人信息系统时最该警惕的事,也是这个项目比一般课程作业更值得认真对待的原因。

## Lab 2 · TrendRadar

### Q1. 关键词匹配的召回率问题在哪里?(宇树 / Unitree / 四足机器人)

**关键词匹配的本质缺陷:它匹配的是字符串,而你想要的是概念。** 这个 gap 有四种典型表现:

| 失败类型 | 例子 | 危害 |
|---|---|---|
| **同义/异名** | 宇树 / Unitree / 宇树科技 | 漏召回 |
| **上下位** | 「四足机器人」是上位概念,提到它未必提到宇树 | 漏召回 |
| **别称/黑话** | 宁德时代 → 「宁王」;英伟达 → 「老黄」 | 漏召回,且中文社区极常见 |
| **一词多义** | 「小米」= 公司 or 谷物;「苹果」同理 | 误召回 |

**三层递进的解法**(我的参考实现覆盖了前两层):

**L1 · 别名词典(立刻能做)** ——`pipeline/keyword.py` 里的 `aliases` 字段:

```yaml
- name: 机器人
  any: ["宇树", "四足机器人", "人形机器人"]
  aliases:
    宇树: ["Unitree", "宇树科技"]
    人形机器人: ["humanoid", "具身智能"]
```

覆盖 60–70% 的问题,成本几乎为零。**别名表要持续维护**,每次发现漏召回就补一条。

**L2 · 消歧上下文** —— 对一词多义的词,要求同时出现共现词:

```yaml
- name: 小米公司
  must: ["小米"]
  any: ["雷军", "手机", "汽车", "SU7", "港股"]   # 排除粮食语境
```

**L3 · 向量召回(Lab 7 补上)** —— 用 embedding 做语义检索,把「查询词」也向量化:

$$ \text{recall}(q) = \{x : \cos(\mathbf{e}_x, \mathbf{e}_q) > \tau\} $$

这才能抓到「某公司发布了新的四足平台」这种一个关键词都没命中、但语义高度相关的内容。

**但注意,不能只用向量。** 正确架构是**并集召回**:

```text
关键词召回(高精度,低召回) ─┐
                            ├─→ 并集 → 精排
向量召回(高召回,低精度)  ─┘
```

关键词保证「我明确关心的一定不漏」(比如你的自选股,漏一条就是真金白银),向量保证「我没想到的也能撞见」。两者是互补而非替代关系——**这是工业搜索系统的标准做法,不是我的发明。**

### Q2. 「项目依赖项目」的链条对可靠性意味着什么?

TrendRadar 的数据源依赖 NewsNow,你又依赖 TrendRadar,链条是:

```text
平台官方接口 → NewsNow → TrendRadar → 你
```

**可用性是乘性的**,不是加性的:

$$ A_{\text{chain}} = \prod_{i=1}^{n} A_i $$

每环 99% 可用,四环串起来是 $0.99^4 \approx 96.1\%$——一个月里有超过一天完全没数据。而且这还是乐观估计,因为**开源项目的可用性远达不到 99%**:作者可能弃坑、可能因为法律压力删库、可能一次重构就改掉接口。

更麻烦的是**故障归因成本**。链条上任一环出问题,你看到的现象都是「今天没数据」。排查时你要逐环去查,而中间环节的日志你根本拿不到。

**在你的系统里,盘一下依赖链**:

| 版面 | 依赖链 | 环数 | 风险 |
|---|---|---|---|
| 热榜 | 平台 → DailyHotApi → 你 | 3 | 中 |
| 订阅 | 平台 → RSSHub → 你 | 3 | 中 |
| 公众号 | 微信 → 第三方服务 → RSSHub → 你 | 4 | **高** |
| 定向 | 平台 → MediaCrawler → 你 | 3 | **高**(反爬对抗中) |

**三条应对策略**:

1. **缩短链条**:直接对接 DailyHotApi 而不是「经 TrendRadar 转手」——这就是我建议你「借鉴 TrendRadar 而不依赖它」的真实理由,不是为了造轮子,是为了少一环。
2. **同源冗余**:关键版面配两条链路。比如财经新闻同时订阅 RSSHub 和官方 RSS,一条挂了另一条顶上。
3. **降级而非失败**:上游挂掉时,用库里的历史数据出一个「近三日回顾」版面,而不是开天窗。**报纸的连续性比单期完整性更重要**。

## Lab 3 · RSSHub

### Q1. RSS 只给最新 N 条,某 UP 主一天发 20 条而你 1 小时轮询一次,会漏吗?

**会,而且这是 RSS 消费方最经典的坑。**

定量:设 feed 长度 $N$(条),发布速率 $\lambda$(条/小时),轮询间隔 $\Delta t$(小时)。不漏的条件是:

$$ \lambda \cdot \Delta t < N $$

即**两次轮询之间产生的新内容,不能超过 feed 能装下的条数**。

举例:B 站某 UP 主 feed 长度 $N = 20$,某天集中发了 20 个视频(约 2 小时内发完,$\lambda = 10$),你 1 小时轮询一次:$10 \times 1 = 10 < 20$,安全。但如果是一个聚合类 feed,比如「财联社快讯」,$\lambda$ 可能到 30 条/小时,而 feed 只有 30 条,那 $30 \times 1 = 30 \not< 30$——**临界,随时漏**。

**实用做法**:

1. **按源分级轮询间隔**,而不是所有源用同一个值:

```yaml
- {name: "某UP主",   interval: 120}   # 低频源, 2 小时够了
- {name: "财联社快讯", interval: 10}    # 高频源, 必须 10 分钟
```

2. **自适应间隔(推荐)**:记录每次轮询的新增条数,动态调整。这也是 NewsNow 的做法,值得抄:

```python
def adapt(prev_interval, new_count, feed_len):
    fill = new_count / feed_len
    if fill > 0.5:   return max(5,  prev_interval // 2)    # 快满了, 加密
    if fill < 0.1:   return min(360, prev_interval * 2)    # 太空了, 放缓
    return prev_interval
```

3. **漏采检测**:如果某次轮询的新增条数 = feed 总长度,几乎可以肯定漏了(feed 被完全刷新)。**记一条 warning 到 `collector_runs`**,在「系统体检」页显示出来。

> 这个「填充率」信号是免费的可观测性,加它只要三行代码,但能让你提前几周发现问题。

### Q2. RSSHub 路由 vs NewsCrawler,本质区别是什么?什么时候用哪个?

看起来都是「网页 → 结构化数据」,但**抽象层次和适用前提完全不同**:

| 维度 | RSSHub 路由 | NewsCrawler / trafilatura |
|---|---|---|
| 输入 | **列表页**(某人的所有文章) | **详情页**(一篇文章的 URL) |
| 输出 | 条目列表(标题+链接+时间) | 单篇正文全文 |
| 核心问题 | **发现**:有什么新内容? | **抽取**:这篇讲了什么? |
| 适配粒度 | 每个站点写一个路由 | 通用启发式 + 少量站点特化 |
| 站点改版 | 路由失效,需要改代码 | 通用算法通常还能撑住 |
| 有无状态 | 无状态(每次全量拉) | 无状态 |

**关键区别一句话:RSSHub 解决「我该读什么」,NewsCrawler 解决「这篇写了什么」。**

它们在你的流水线里是**串联**而非二选一:

```text
RSSHub(发现) → items 入库(只有标题+链接)
                      ↓
          NewsCrawler / trafilatura(抽取)
                      ↓
              回填 items.content
                      ↓
                    LLM
```

**唯一的例外**:部分 RSS 源在 `content:encoded` 里直接给全文。这时抽取步骤可以跳过——**先检查再请求,能省掉大量无谓的网络往返**,也更礼貌。我的参考实现在 `RSSCollector` 里就是先取 `content:encoded`。

### Q3. RSSHub 彻底不可用,你损失哪几个版面?这个风险你接受吗? ⚖️

按我给的架构盘点:

| 版面 | 依赖 RSSHub? | 损失程度 |
|---|---|---|
| 热榜速览 | 否(走 DailyHotApi) | 无 |
| 深度阅读(知乎) | **是** | **全损** |
| 公众号 | **是** | **全损** |
| B站新番/UP主 | **是** | **全损** |
| 财经新闻 | 部分(部分源有官方 RSS) | 半损 |
| 定向采集 | 否(走 MediaCrawler) | 无 |

**结论:约 60% 的版面依赖单一组件。这是不可接受的单点故障。**

但——**「不可接受」不等于「要立刻消除」**。正确的工程判断是分级应对:

1. **自部署已经消除了大部分风险**。RSSHub 不可用的主要现实场景是「公共实例挂了/限流」,自部署后剩下的风险只有「项目弃坑 + 路由随站点改版失效」,而这是渐进的、可感知的,不是一夜暴毙。
2. **对不可替代的源,做本地路由备份**。你在 Lab 3.5 自己写过一个路由,说明你有能力在某个关键路由失效时自己修。**这就是那个练习的真实价值**——不是为了提 PR,是为了让你不受制于人。
3. **加监控**:「系统体检」页跟踪每个 feed 的填充率与失败率,让退化在造成损失前被看见。

> 我的判断是**接受这个风险**,理由是:自部署 + 有能力自修路由 + 有监控,三者叠加后残余风险已经低于「因为过度设计而做不完项目」的风险。**对个人项目,按时交付本身就是最重要的可靠性指标。**

## Lab 4 · MediaCrawler

### Q1. 「订阅式采集」与「搜索式采集」在风险、成本、数据质量上的差异

这是本 Lab 最重要的一道题,因为它决定你的架构选型。

| 维度 | 订阅式(RSS,目标已知) | 搜索式(关键词,目标未知) |
|---|---|---|
| **请求量** | $O(\text{订阅数})$,恒定 | $O(\text{关键词} \times \text{页数})$,易爆炸 |
| **请求特征** | 固定 URL、固定频率 → 像正常用户 | 大量翻页、大量不同 query → **像爬虫** |
| **被封风险** | 低 | **高**,且需要登录态,封的是你的账号 |
| **技术复杂度** | 低,`feedparser` 一行 | 高:签名、验证码、代理池、Playwright |
| **法律风险** | 低,公开订阅接口 | 中高,常需绕过接口保护 |
| **召回率** | 低——只能拿到你已知的源 | 高——能发现未知作者 |
| **精确率** | **高**——源是你亲自选的 | 低——搜索结果含大量营销号 |
| **数据新鲜度** | 依赖轮询间隔 | 请求即得 |
| **维护成本** | 低,RSSHub 社区帮你维护 | **高,反爬持续对抗** |

**核心洞察:两者的差异根源是「你是否已经知道要什么」。**

- 已知目标(你订阅的博主、公众号、UP主)→ 订阅式,**在各个维度上全面占优**
- 未知目标(某关键词下全网在说什么)→ 只能搜索式,代价是全套复杂度

**对你的愿景做映射**,结论很清楚:

| 你的需求 | 该用哪种 | 理由 |
|---|---|---|
| 指定公众号 | 订阅式 | 目标已知 |
| 指定 B站 UP主 / 新番 | 订阅式 | 目标已知 |
| 指定博主帖子 | 订阅式(若在 B站/知乎/微博) | RSSHub 已覆盖 |
| 知乎优质长文 | 订阅式 + 个性化排序 | 你要的是「好」不是「全」 |
| 自选股新闻 | 订阅式(财经 RSS + akshare) | 有官方接口 |
| 微博热点 | 订阅式(热榜 API) | 热榜就是现成的聚合 |
| **小红书/抖音指定博主** | **搜索式** | 无 RSS 通道 |

**结论:你的需求里只有最后一项非搜索式不可。** 这就是我把 MediaCrawler 排在最后、并说它可以砍掉的定量依据——不是拍脑袋,是这张表算出来的。

### Q2. robots.txt、服务条款、法律,三者约束力有何不同?个人自用与对外服务的界线在哪?

**约束力递增的三层**:

| 层级 | 性质 | 违反后果 | 强制力 |
|---|---|---|---|
| **robots.txt** | 行业惯例,技术声明 | 通常无直接后果 | 无法律强制力,但**在诉讼中是重要证据**——证明你「明知故犯」 |
| **服务条款(ToS)** | 民事合同 | 封号、断开访问、民事索赔 | 有,但需对方主张;注册即视为同意 |
| **法律法规** | 强制性规范 | 行政处罚,情节严重涉刑 | 最强,不以任何人意志为转移 |

**中国大陆需要注意的具体法律**(我不是律师,以下是通识层面的提示,涉及实际风险请咨询专业人士):

- **《网络安全法》《数据安全法》《个人信息保护法》**——个人信息的收集处理有严格要求
- **《刑法》第 285 条**「非法获取计算机信息系统数据罪」——**绕过技术保护措施**是关键要件。这条是爬虫领域最需要警惕的:破解签名算法、绕过验证码,性质上就已经不同于「读取公开页面」了
- **《反不正当竞争法》**——主要针对商业场景的数据抓取

**个人自用与对外服务的界线**,我认为有四条判据,**任何一条越线,性质就变了**:

| 判据 | 个人自用 | 越线 |
|---|---|---|
| **分发** | 只有你自己看 | 公开网站、群发、提供 API |
| **规模** | 每天几百条,人能读完 | 全站扫描、批量入库 |
| **牟利** | 无 | 收费、导流、广告 |
| **替代性** | 不影响原站访问 | 你的产品让人不必去原站 |

**最后一条最容易被忽略,但它是版权法里「市场替代」的核心判据。** 如果你的 PDF 里放了公众号全文,读者再也不用点开原文——那你就构成了对原作品市场的替代。这直接连到 Lab 5 Q2。

**给你的具体建议**:在 README 顶部写明用途声明,把 MediaCrawler 的并发设为 1、间隔设为 6 小时,只抓你真正订阅的那几个博主。**这不是形式主义——它让你在四条判据上都清清楚楚地站在安全一侧。**

### Q3. 平台明确禁止抓取而你又需要,替代方案是什么?

按**优先级**排序,前面的用尽再考虑后面的:

1. **官方 API / 开放平台**。多数平台有,只是需要申请、有配额。麻烦但完全合规,长期最省心。
2. **官方 RSS / 订阅功能**。很多站点自己就提供,只是不显眼。**先找,别急着写爬虫。**
3. **邮件订阅 → 邮箱解析**。很多媒体有邮件 newsletter。你订阅到一个专用邮箱,然后用 IMAP 读取解析。**完全合规,而且新鲜度极高**,这条路被严重低估了。
4. **官方客户端 + 手动触发**。比如公众号,你手动把感兴趣的文章转发到一个「稍后读」入口,系统只负责抓取你主动投喂的链接。半自动,但零风险。
5. **换等价信源**。同一新闻通常有多家报道,换一个不禁止抓取的源即可。**对新闻类内容,这是最优解**——你要的是事实,不是特定平台。
6. **放弃这个版面**。

> **认真说:选项 6 是一个合格工程师的正常选择,不是失败。** 一个能长期稳定运行、合规、你敢公开讲的系统,价值远大于一个功能齐全但随时可能出事的系统。

## Lab 5 · 正文抽取

### Q1. 付费墙 / 需要登录 / 纯图片的公众号文章,分别怎么处理?

| 类型 | 处理方式 | 理由 |
|---|---|---|
| **硬付费墙** | 只存标题 + 官方摘要,**标注「需订阅」** | 绕过付费墙在法律和道德上都站不住,别碰 |
| **软墙(前 N 段免费)** | 抽取免费部分,标注截断 | 这是站方主动公开的内容 |
| **需登录但免费** | ⚖️ 用你自己的账号 Cookie,严格限速 | 灰色地带。判据是「你作为用户本来就有权看」。但注意封号风险由你承担 |
| **纯图片文章** | 降级:标题 + 首图 + 链接。**不建议上 OCR** | OCR 成本高、错误率高,且图片文章多为营销内容,价值密度低 |
| **JS 渲染** | trafilatura 失败后再上 Playwright | Playwright 慢 10 倍,只在必要时用 |

**架构上要做的是「分级降级」而不是「要么成功要么失败」**:

```python
QUALITY_TIERS = [
    ("full",      lambda r: r.text and len(r.text) > 500),
    ("partial",   lambda r: r.text and len(r.text) > 150),
    ("meta_only", lambda r: bool(r.title)),
]
```

把 tier 存进库,渲染时按 tier 决定展示形态:`full` 给 LLM 摘要,`meta_only` 只列标题。**报纸上永远不出现空条目**,这是 Lab 6「失败隔离」原则在内容层的体现。

### Q2. ★ 你在本地存了他人完整作品。PDF 里该放全文还是摘要 + 链接? ⚖️

**我的答案:放摘要 + 链接,不放全文。而且这不只是法律考虑,更是产品考虑。**

**法律层面**:「个人自用」在著作权法上确实有较宽的空间(合理使用),但要注意——你的本地数据库和你分发出去的 PDF 是**两回事**:

- 抓取存库供自己检索 → 空间较大
- 生成 PDF 存到本地自己读 → 仍属个人使用
- 把 PDF 发到群里、发给朋友、放上博客 → **性质完全改变,构成复制发行**

而 PDF 是一种**天然易于传播**的格式。你今天说只给自己看,三个月后觉得做得不错随手分享,就越线了。**架构上把这条路堵死,比依赖自律更可靠。**

**产品层面(这一点更重要)**:

一份 30 页塞满全文的 PDF,你在早餐 10 分钟里**根本读不完**,结果是你会开始跳过它,最终不再打开——这个项目就死了。

而一份 4 页、每条只有标题 + 3 行摘要 + 一个「为什么值得读」的 PDF,你能扫完,然后**主动点开那 2–3 条真正感兴趣的**。这才是可持续的阅读方式。

> **报纸的价值在于「帮你决定读什么」,不在于「替你读完」。** 这是它区别于 RSS 阅读器的根本。

**具体建议**:

```markdown
### 标题(来源 · 作者 · 2小时前)
> LLM 摘要 2–3 句,必须包含「核心结论」
**为什么给你**:命中「自选股-宁德时代」+ 与你收藏的《XX》相似度 0.83
[原文](url) · 全文约 3200 字 · 预计 8 分钟
```

「为什么给你」这一行是**可解释性**,它让你能判断系统是不是在瞎推,也让你知道该怎么调关键词表。**这一行会让你的系统从「黑箱」变成「工具」**,强烈建议加上。

## Lab 6 · 调度与可靠性

### Q1. 系统该跑在哪?树莓派 / 云服务器 / GitHub Actions ⚖️

| 维度 | 树莓派(家里) | 云服务器 | GitHub Actions |
|---|---|---|---|
| 成本 | 一次性 ~400 元 | 30–60 元/月 | 免费(公开仓库) |
| 可用性 | 依赖家里电和网 | 高 | 高但有排队 |
| **IP 环境** | **家庭住宅 IP,最不容易被风控** | 机房 IP,**易被识别为爬虫** | 云 IP,**很多站点直接封** |
| 持久化 | 本地磁盘,天然持久 | 云盘 | **无状态,必须外挂存储** |
| 登录态 | 稳定 | 需要维护 | 每次全新环境,**Cookie 易失效** |
| 长任务 | 无限制 | 无限制 | 单任务 6 小时上限 |
| 调试 | 方便 | SSH | **难,只能看日志** |

**我的推荐:树莓派 / 家里的旧笔记本 / NAS。**

决定性理由是**第三行**:家庭住宅 IP 在平台风控模型里的信任度远高于机房 IP。你的系统要访问微博、知乎、B站,机房 IP 会显著提高触发验证码和封禁的概率。这个因素的重要性超过成本和可用性。

次要理由:Cookie 和登录态可以长期稳定保存,不用反复重新登录。

**混合方案(如果你想更稳)**:

```text
树莓派:采集 + 存储(需要好 IP 和持久化)
   ↓ 只同步结果数据
云服务器:LLM 调用 + 渲染 + 推送(需要高可用和好网络)
```

### Q2. 早上 7 点 pipeline 跑到一半崩了,你希望发生什么? ⚖️

**我的答案:出一份残缺的报,并在报头明确标注哪些版面缺失。绝不静默失败,也不因单点失败而不出报。**

三个选项的对比:

| 策略 | 后果 |
|---|---|
| **不出报只告警** | 你早上没报纸看,连续两次你就不看了。**产品死亡** |
| **无限重试直到成功** | 可能永远出不来,或者 10 点才推送 —— 那时你已经在通勤路上 |
| **超时熔断 + 残缺出报** ✅ | 你总能拿到东西,且知道缺了什么 |

**实现要点**:

```python
def produce_edition(edition: str, deadline_minutes: int = 20):
    """每个版面独立生成,单个版面失败不影响其他版面。"""
    sections, failures = [], []
    for sec in SECTIONS:
        try:
            sections.append(with_timeout(sec.render, seconds=180))
        except Exception as e:
            failures.append((sec.name, repr(e)))
            sections.append(sec.placeholder())   # 「本版面今日无数据」
    # 只要有一个版面成功就出报
    if any(s.has_content for s in sections):
        render_pdf(sections, failures_note=failures)
        push()
    else:
        alert("全部版面失败")   # 只有这种情况才不出报
```

两个关键设计:

1. **`deadline` 是硬约束**。到点必须出报,宁可少几个版面。**早报的价值 90% 在「7:30 送到」这件事上**,晚到的完整报纸不如准时的残缺报纸。
2. **失败信息进报纸,不进日志**。写进日志你永远不会看;印在报纸最后一页,你每天扫一眼就完成了运维巡检。

### Q3. GitHub Actions 免费额度能跑这个系统吗?有什么隐患?

**额度算得过来,但隐患让它不适合做主力。**

额度:公开仓库的 Actions 分钟数免费。按每小时跑一次、每次 3 分钟算,一个月约 2160 分钟——公开仓库无所谓,**私有仓库会超**(免费档 2000 分钟/月)。

**但真正的问题不是额度,是这五条**:

1. **IP 被封**。GitHub Actions 的 IP 段是公开已知的,大量平台直接对其做限制。这条是致命的。
2. **无状态**。每次全新容器,SQLite 必须 commit 回仓库或外挂对象存储。commit 回仓库意味着你的**数据全部公开**——包括你的阅读偏好,这是很敏感的个人数据。
3. **Cookie/登录态无处安放**。放 Secrets 里可以,但过期后无法自动续期。
4. **调度不准**。GitHub 明确说明 cron 可能延迟,高峰期延迟十几分钟很常见。你的 7:30 早报可能 7:50 才到。
5. **ToS 风险**。GitHub 的服务条款对「持续性的自动化爬取」是有态度的,大规模用它跑爬虫可能被判定滥用。

**合理用法:把它当作备份和分发通道,而不是主力运行时。**

```text
树莓派:主力采集 + pipeline + 渲染
   ↓
GitHub Actions:定时健康检查 —— 如果 6 小时没收到心跳,发告警
```

这样你既拿到了「主力挂了有人通知你」的好处,又避开了全部五条隐患。

## Lab 7 · 个性化排序

### Q1. ★ 黄金集来自过去的收藏 → 信息茧房。怎么在打分函数里留探索的口子?

**先说清楚机制,再说解法。**

茧房的形成是一个**正反馈闭环**:

$$ \text{收藏}_t \rightarrow \text{画像}_t \rightarrow \text{推荐}_{t+1} \rightarrow \text{收藏}_{t+1} \rightarrow \text{画像}_{t+1} \rightarrow \cdots $$

每一轮,画像的方差都在收缩。**几个月后,你的系统会变成一个只会说你爱听的话的回声室**——而且因为它是你自己写的,你会格外信任它,这比商业推荐系统的茧房更危险。

**四条解法,建议全部实施**:

**① $\epsilon$-greedy 版位配额(参考实现 `apply_exploration`)**

固定留出 15% 版位给「低相似度 + 高 LLM 质量分」的内容。注意**不是纯随机探索**——纯随机只会给你垃圾,一周后你就把这个功能关掉了。要在**高质量的陌生内容**里随机:

```python
pool = [x for x in candidates if sim(x) < 0.55 and llm_score(x) >= 0.7]
```

**② 多样性重排(MMR)**

选完第 $k$ 条后,后续候选按「与已选内容的最大相似度」做惩罚:

$$ \text{MMR}(x) = \lambda \cdot S(x) - (1-\lambda) \cdot \max_{y \in \text{selected}} \cos(\mathbf{e}_x, \mathbf{e}_y) $$

这保证同一版面里 10 条内容不会全是同一个话题的不同角度。$\lambda$ 取 0.7 左右。

**③ 主动引入对立信源**

给「立场/风格与你惯常阅读相反」的源**固定版位**,不参与排名竞争。理由前面说过:让它们竞争排名它们必输,因为打分函数就是按你的口味训练的。

**④ 画像衰减**

黄金集里的样本按时间加权,半年前的收藏权重减半:

$$ w_i = 0.5^{\,\text{age}_i / 180\text{d}} $$

这让画像跟着你成长,而不是把你锁死在大二时的兴趣上。

> **诚实的补充:以上四条都是缓解,不是根治。** 根治需要你定期**人工**做一件事:每月翻一次「被系统淘汰的高分内容」列表,看看有没有明明该推给你却被埋了的。这个动作没法自动化,但它是你保持对系统的控制权的方式。

### Q2. LLM 评委本身有偏见,可能系统性偏爱某种文风。怎么检测?

**先承认这是真的。** LLM 的偏好来自训练数据和 RLHF,已知的系统性倾向包括:偏好结构化、显式论证、学术腔的文本;倾向给长文本更高分;对中文口语化写作、反讽、含蓄表达打分偏低。这意味着**大量优秀的中文随笔和杂文会被你的系统低估**。

**四种检测方法,按成本从低到高**:

**① 分层统计(最便宜,先做这个)**

按来源/文体/长度分组,看 LLM 分的分布:

```sql
SELECT source, kind,
       COUNT(*) AS n,
       AVG(llm_score) AS mean,
       AVG(LENGTH(content)) AS avg_len
FROM items WHERE llm_score IS NOT NULL
GROUP BY source, kind;
```

如果某个来源的均分显著低于其他,先别急着下结论——可能确实质量差。但如果**你自己读过觉得不差**,那就是偏见信号。

**② 长度混淆检验**

算 LLM 分与文本长度的相关系数 $r$。如果 $r > 0.5$,说明它主要在给长度打分,而不是给质量打分。**这是最常见的一种偏见,而且最容易修**:在 prompt 里显式要求「不要因为文章长就给高分」,并在评分时截断到固定长度。

**③ 位置/顺序检验**

同一批内容打乱顺序再评一次,看分数是否稳定。如果不稳定,说明存在位置偏见或随机性过大——那你需要提高 `temperature=0` 或做多次采样取中位数。

**④ 人工对照集(最准,值得做一次)**

你手工标注 30 条(15 高 15 低),让 LLM 评,算 Spearman 相关系数。

$$ \rho > 0.6 \Rightarrow \text{可用};\quad \rho < 0.3 \Rightarrow \text{rubric 需重写} $$

**这 30 条标注花你一小时,但它是你唯一能量化「我的评委靠不靠谱」的手段。** 强烈建议做,而且每次改 rubric 后重跑一遍。

### Q3. 权重 $w_i$ 怎么定?拍脑袋、网格搜索、还是从反馈学? ⚖️

**答:三个阶段依次使用。这不是三选一,是一条演进路径。**

**阶段一(第 1–2 周):拍脑袋,但要有原则**

冷启动时你没有任何数据,网格搜索无从搜起——**没有标注就没有目标函数**。所以只能拍,但按这三条原则拍:

1. 归一化:$\sum w_i = 1$,便于解释
2. 按信息量分配:你最信任的信号给最大权重。个人化信号($S_{\text{sim}}$)和质量信号($S_{\text{llm}}$)应该占大头
3. 早晚报差异化:早报 $w_{\text{hot}}$ 高,晚报 $w_{\text{sim}}$ 和 $w_{\text{len}}$ 高

我的参考实现给了 `Weights.morning()` 和 `Weights.evening()` 两组初值,可以直接用。

**阶段二(第 3–6 周):网格搜索 + 人工盲评**

积累 2–3 周数据后,固定一天的候选池,用不同权重组合生成 3 份报纸,**遮住权重配置**让自己盲评。这是 Lab 8 验收标准里那条 A/B 自评的正式做法。

搜索空间别太大——5 个权重每个 3 档就是 243 种组合,你评不完。**先做一维扫描**:固定其他权重,只扫 $w_{\text{sim}}$,找出拐点。

**阶段三(第 8 周后):从反馈学**

积累 200+ 条反馈标注后,用逻辑回归学权重:

$$ P(\text{有用} \mid x) = \sigma\!\left(\sum_i w_i S_i(x) + b\right) $$

用 L2 正则防止过拟合(样本量小时很容易过拟合),学到的 $w_i$ 直接就是新权重。**逻辑回归而不是更复杂的模型,因为你的样本量只有几百,而且你需要权重可解释。**

**三个必须注意的陷阱**:

1. **反馈是有偏的**。你只能对「被推荐了的内容」打标签,没被推荐的永远拿不到反馈。这是经典的 selection bias。**探索版位的存在同时也在为你收集无偏样本**——这是探索机制的第二个作用,很多人只想到第一个。
2. **别过早自动化**。前 8 周手动调权重,你会对每个信号的作用建立直觉。直接上自动优化,你会失去这份理解,而且模型出问题时不知道怎么办。
3. **保留手动覆盖**。不管学出什么权重,`config` 里的手动值优先。**你才是这份报纸的主编。**

## Lab 8 · 渲染

### Q1. 要不要同时输出 EPUB 或响应式 HTML? ⚖️

**答:要,但优先级是 HTML > PDF > EPUB,而且第一版只做 HTML + PDF。**

| 格式 | 优势 | 劣势 | 适用场景 |
|---|---|---|---|
| **HTML** | 可点击、响应式、可交互(反馈按钮)、生成快 | 不便归档,需要有个地方托管 | **手机上快速扫读**——这才是你早餐时的真实场景 |
| **PDF** | 排版精确、易归档、可打印、离线 | 手机阅读体验差、不可点击 | 长期归档、周末回顾 |
| EPUB | 阅读器体验好、可调字号 | 多一条链路,收益重叠 | 有 Kindle/墨水屏才值得 |

**关键判断:你说"早晨和晚饭时间推送",那大概率是在手机上看。** 手机上 PDF 的体验是明显差的——要缩放、不能点链接、加载慢。所以**真实主力格式应该是 HTML**,PDF 作为归档副本。

推荐做法:

```text
digest.md ──┬─→ digest.html  → 邮件正文内联 + 手机上点开就读
            └─→ digest.pdf   → 邮件附件, 归档用
```

邮件正文内联 HTML 是这里的关键技巧:你打开邮件就直接看到报纸,不需要点开附件。这个体验差异会显著影响你能不能坚持每天读。

**Lab 8 的 `render/` 分层设计正好支持这个**——因为中间层是 Markdown,加一个输出格式只是加一个渲染器,不用动 pipeline。**这就是当初坚持要有 Markdown 中间层的回报。**

### Q2. 某天只采到 5 条内容,报纸该怎么呈现?

**原则:空版面比错误更伤害体验,但「假装正常」比空版面更糟。**

分级策略:

| 内容量 | 呈现方式 |
|---|---|
| 正常(30+) | 完整版面 |
| 偏少(10–30) | 合并版面,减少小标题,**不填充凑数** |
| 很少(3–10) | 单页简报模式 + **显著的系统告警** |
| 极少(0–3) | 切换到「回顾模式」:出「近三日未读精选」 |

**三条具体规则**:

1. **绝不用低分内容填充版位**。你的打分函数应该有**绝对阈值**而不只是相对排名——分数低于 0.3 的内容,哪怕是当天最高分也不上报。一旦开始凑数,你会很快学会跳过这个版面。
2. **内容少时必须告警**。这几乎总是系统故障(某个 collector 挂了),而不是「今天世界很平静」。把「体检页」提到第一页。
3. **回顾模式是个好兜底**。库里永远有未读的历史内容,`used_in IS NULL` 一查就有。**报纸的连续性比单期的时效性更重要**——这条原则在 Lab 2 Q2 里也出现过,它是这个系统的一条主线。

## 最后:关于「标答」这两个字

这份文档里,**只有约三分之一的题有唯一答案**(数据契约、幂等实现、采样定理、SimHash 原理这类)。剩下标了 ⚖️ 的部分,我给的是判断加依据,你完全可能得出不同结论。

判断的价值在依据里,不在结论里。你在 ADR 里写清楚「我选了 A,因为在我的约束下 X 比 Y 重要」——哪怕三个月后你推翻它,那份推理过程也已经是你的了。

而这个,恰好就是把「会用爬虫框架的人」和「能设计信息系统的人」区分开的东西。
